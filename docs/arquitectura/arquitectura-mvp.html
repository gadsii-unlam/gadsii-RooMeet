Arquitectura del MVP de RooMeet, tal como está en el código

Relevada leyendo mvp/ en la rama mvp (commit ec1d439). Es una SPA de React + TypeScript que corre entera en el navegador: no hay backend, base de datos, API ni conexión con SIU Guaraní. La clasificación construido / simulado sigue la tabla 8.2 del brief (TP3).

Dónde están los datos

  • Dataset de entrada: constante TypeScript compilada en el JavaScript que sirve Vercel. Solo lectura; cambia únicamente con un nuevo deploy (DATASET_VERSION).
  • Sesión en curso: SessionState en memoria de React. Es la única fuente de las asignaciones; filtros y selección son estado de UI aparte.
  • Persistencia: copia JSON en localStorage bajo roomeet:mvp:session:v6, escrita después de cada cambio y validada al recargar. Si el navegador la bloquea, la app sigue en memoria y avisa.
  • Evidencia: archivo JSON que descarga el usuario (dataset, propuesta original y final, eventos, métricas).
  • Asset: mapa-campus.png, extraído del wireframe por un script y servido como archivo estático.
  • No hay base de datos, servidor ni almacenamiento compartido entre usuarios.

Diferencias con la guía de implementación

Este diagrama describe el código, no MVP-AGENTES.md. Las diferencias encontradas:

  • La guía prevé components/AssignmentTable.tsx; no existe. La tabla está dentro de ProposalScreen.
  • La lógica de deshacer (revalidar y restaurar) vive en App.tsx, no en el dominio; el reducer aplica el resultado sin volver a validar.
  • Los filtros de monitoreo son día y cuatro franjas fijas en monitoring.ts, no intervalos derivados del dataset.
  • La clave de almacenamiento es …:v6 (la guía dice v5) y schemaVersion sigue en 4.
  • Las pantallas importan el dataset directamente, por lo que la capa de presentación depende de la de datos además de recibir props de App.
